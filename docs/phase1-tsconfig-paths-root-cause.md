# Medusa CLI `tsconfig-paths` Compatibility Finding

**Status:** Reproduced and corrected in the Phase 1 CI environment; independent review still required.

## Evidence

The original migration log showed this path through the installed code:

- Caller: `node_modules/@medusajs/cli/cli.js:5`
- Installed `@medusajs/cli`: `2.22.1`
- Installed `tsconfig-paths`: `3.15.0`
- Original call shape: `register({})`
- Runtime exception: `TypeError: The "path" argument must be of type string. Received undefined`, from `tsconfig-paths/src/config-loader.ts`.

The same workflow's independent config probe loaded `apps/backend/tsconfig.json` successfully and resolved its absolute base URL to `apps/backend`. This separated the issue from a malformed/missing tsconfig.

## Guarded correction

The root `postinstall` hook runs `scripts/patch-medusa-cli-tsconfig-paths.cjs`. It only proceeds for Medusa CLI `2.22.1` and only if it finds the expected `register({})` call; it changes it to `register()`. Unexpected CLI versions or source shapes fail the install rather than silently applying an unreviewed edit.

The CI diagnostic step now checks:
1. Expected Medusa CLI and `tsconfig-paths` versions.
2. Installed CLI source uses `register()` with no empty options object.
3. Backend `tsconfig.json` loads and resolves its base URL.
4. Calling `register()` succeeds without a trace preload.

The migration step no longer sets `NODE_OPTIONS` or prints a repeated call stack. The diagnostic result is preserved at `artifacts/medusa-loader-diagnostic.log`, and the install log records whether the guarded patch was applied.

## Limitations and next gate

This is a local, guarded compatibility patch to the installed CLI, not an upstream fix. A clean `npm ci`, migration, backend/storefront build, and Redis adapter suite are required on every relevant revision. The lockfile generated by CI is still a candidate artifact and must be reviewed/committed before clean-install reproducibility can be considered closed.
